# LEARNED.md — Append-Only Lessons Log

Lessons from owner corrections and self-caught mistakes, appended by AI agents
per the Debugging Protocols section of CLAUDE.md. Never rewrite or delete an
existing entry — refine a similar lesson in place instead of duplicating it.
On conflict with CLAUDE.md, this file wins.

Entry format:
`- YYYY-MM-DD [status]: <rule> (trigger: <what went wrong>)`

One lesson per entry. An entry may run to a paragraph — several of the most
useful ones do. Do not compress a lesson to fit a line.

The status tag says whether a lesson is still carried in prose or has been made
mechanical. Promoting an entry is the point; the `new-audit` skill exists for it.

A tag may be CORRECTED in place. The no-rewrite rule above protects a lesson's
text, not its status line: a tag is a claim about which mechanism carries the
lesson today, so when that changes — or when it was wrong when written — change
it and note the correction with a date inside the entry. A stale tag understates
the repo's coverage and draws promotion pressure at a lesson that already has a
fence, which is how the 2026-08-13 `git checkout` entry stayed unpromoted for a
week after a hook had already mechanised it.

- `[audit]`    enforced by a script in tests/, run by `npm test`
- `[tool]`     mechanical, but ON DEMAND rather than in `npm test` — the rule is
               executable and nothing runs it for you (`npm run mutate`). Added
               2026-08-14: tagging such a lesson `[audit]` reads as "this is
               enforced on every commit", which is a stronger claim than the
               thing makes, and the whole point of these tags is that the claim
               matches the mechanism.
- `[hook]`     enforced by a hook in .claude/hooks/
- `[skill]`    encoded as a step in a skill under .claude/skills/
- `[advisory]` carried in prose only — still live risk

- 2026-07-30 [audit]: An exponential approach (slew, smoothing, easing) stored in a HALF-FLOAT buffer freezes short of its target — near 1.0 one ulp is ~1e-3, so once the per-frame step falls below that it rounds to no change and never arrives. Replace any step smaller than an ulp with exactly one ulp in the right direction, clamped against overshoot. And sample convergence at TWO horizons: a stall is indistinguishable from convergence if you only look once (trigger: rutt slew sat at 98.51 vs 100.91, bit-identical at frame 300 and frame 2000; the first guess was resampling through the history buffer, disproved by measuring the resampled-no-lag reference at 100.906). REFINED 2026-08-05 — the rule is not about half-float, it is about ANY exponential accumulator whose per-frame step can fall below one representable level, and the fix is not always a progress floor: sometimes it is simply the right buffer. Motion Extraction repeated this in an 8-BIT background, which is 8x coarser than half: `mix(bg, cur, adapt)` at `Bg adapt` 4s gives a step of 2.9e-3 against an 8-bit level of 3.9e-3, so the background froze on the frame it was primed with and NEVER moved again — above ~2.95s nothing could move it for any difference at all, including full black-to-white. It did not look like a precision bug: it looked like a beautiful static reference plate, and produced clean silhouettes, so it read as the feature working until the owner noticed it was always the first frame. Float32 was chosen over a progress floor because a floor relinearises the tail and would have made the long end of a 0–10s range a lie; measured 8-bit closed 2% of a gap in 10s where float32 closed the specified 82%. **Before storing an exponential in any buffer, divide the smallest per-frame step by the buffer's resolution and check the quotient is comfortably above 1.**

- 2026-07-31 [skill]: Two verification traps in one session, both of which produce numbers that look fine. REFINED 2026-08-14 — **a cache-busting query string is NOT enough, and believing it is turns this from a five-second fix into a wrong diagnosis.** `?v=N` gets a fresh *response for that URL*, but the service worker still serves the cached `index.html`, which names the OLD hashed bundle — so the page loads `index-CnpocEWc.js` after a build that produced `index-K7MN9JKd.js`, and the new code is not merely stale, it is entirely absent. - 2026-07-31 [advisory]: Before taking over a channel that currently holds a constant, find out what the CONSUMER wants from it. Packing SDF depth into alpha looked free — alpha was a constant 1.0 and nothing read it — but it (a) silently enabled NormalBlending's src.a multiply, dimming every hit by its own depth and multiplying every MISS by zero, which deleted the background aura, and (b) spent the one channel the compositor needs to know where the source IS, closing the keyer's Alpha mode, which was the correct fix for the owner's actual complaint. "Unused" meant "not yet used", not "free". A full-screen write into a source target wants the shader's RGBA verbatim: set `blending: THREE.NoBlending`. REFINED 2026-08-02 — three.js only applies blending when the material opts in: `(blending === NormalBlending && transparent === false) ? NoBlending : blending` (three.cjs, verified in node_modules). So a plain opaque ShaderMaterial is already safe, and the dangerous combination is specifically `transparent: true` (or any non-Normal mode) together with non-constant alpha. That is why this resisted promotion to an audit: the natural file-level rule flags ParticleRender and ParticleSystem, where `transparent: true` belongs to the Points material that is SUPPOSED to blend additively, not to the full-screen quad — 2 false positives out of 16. Stays [advisory] until per-material association is worth the parser (trigger: owner reported a dull glow, then a black halo; both were this, two turns apart).
- 2026-07-31 [advisory]: Do not let one variable control both WHERE a gradient is and HOW BRIGHT it is — the falloff will extinguish the far stop and that stop becomes unreachable at any setting. Aura brightness used halo^2 while the colour mix used halo, so by 76% of the way to Hue 2 luma was 0.010: the second colour of a two-colour gradient could be set to anything and never appeared. Same shape of bug as a multiply-by-environment that can reach zero (Glow Env took the aura to luma 0.004 over dark surround) — normalise to take the hue and leave the level alone. And a matte composite `mix(bg,fg,a)` is BACKWARDS for anything emissive: a glow adds light rather than occluding, so the background shows through it as shadows; use `bg*(1-a)+fg` (trigger: three wrong diagnoses of "no outer glow" before reconstructing the fragment path numerically against the owner's real slider values).

- 2026-08-04 [skill]: A metric that is CAPPED cannot answer a question about cost. Four soak phases on a real iPad returned avg_ms 16.675 / 16.670 / 16.670 / 16.670 for deck-B-empty, loaded-idle, both-live and recovered — all four pinned at the 16.67ms vsync ceiling, because the device was never saturated. "The idle-deck gate fires" and "the deck uploads and there is headroom to absorb it" are INDISTINGUISHABLE in frame time by construction, so the phase-2-vs-phase-1 comparison the protocol is built around could only ever produce a PASS that means nothing. Extends the 2026-07-30 saturation lesson (beam width at 60 lines) from "pick a metric the control can move" to "check the metric is not already at its limit before the run, not after". The fix was not a longer soak but a different observable: three integer counters in MovieInput.uploadIfNewFrame (ticks/gated/uploads) settled it in 65 seconds — deckB gated 3917 with uploads frozen at xfade 0, then uploads +46616 with gated 0 at xfade 0.5. Count the EVENT you care about; do not infer it from an aggregate that something else is clamping (trigger: 55 minutes of measured phases that answered the thermal question and could not, even in principle, answer the gating one).
- 2026-08-04 [skill]: A console readback that does not clear on navigation will show you a log you just DELETED. - 2026-08-04 [audit]: **"three still exports the constant" is not "three still supports the upload."** `THREE.RGBFormat` still resolves in r168 — it is in the constant table, `WebGLUtils.convert` maps it to `gl.RGB`, and nothing is undefined or warns — but `getInternalFormat` picks no SIZED internal format for RGB (it upgrades RED/RG/RGBA and only touches RGB for `UNSIGNED_INT_5_9_9_9_REV`). So `RGBFormat + FloatType` went out as unsized RGB + FLOAT, which WebGL2 rejects: `texImage2D` raised INVALID_OPERATION, the texture stayed incomplete, and every `texture2D()` against it returned (0,0,0,1). Load a .cube, raise LUT Amount, whole picture black — the colour grade panel had never worked in WebGL2. Verifying that a name resolves proves nothing; the constant table and `getInternalFormat` disagree and only the second one runs, so read the conversion path in `node_modules/three` rather than checking the export exists. The second half is the same bug one device away: a linearly filtered **RGBA32F** needs `OES_texture_float_linear` and samples black without it, while **RGBA16F** is filterable in core WebGL2 — so half-float is the correct storage for anything sampled with LinearFilter, and the desk would never have shown the difference. Nothing downstream can catch either one, because solid black is a picture this instrument is allowed to produce (trigger: owner reported "loading a .cube and adding LUT amount turns the image to black"; the first hypothesis — that r152 removed the constant — was wrong in its reason and right in its fix, and the real mechanism only came out of reading getInternalFormat and then reproducing INVALID_OPERATION against a real WebGL2 context).
- 2026-08-04 [skill]: A colour-transform fixture must be chosen so that the transform CANNOT be confused with the input — the obvious choices all hide it. Verifying the LUT fix in-app, an R↔B swap was invisible because the default Noise source is greyscale (r==g==b, so the swap is the identity), and an invert of greyscale noise still looks like greyscale noise. Neither read as a failed test; both read as "the LUT is not doing anything", which is exactly the bug's own symptom. A **constant-colour `.cube`** (every one of the N³ entries magenta) settles it in one screenshot: the whole canvas must become that colour regardless of input, so "applied" and "not applied" cannot be mistaken for each other, and sweeping the amount 0 → 50 → 100 then proves the blend rather than just the endpoint. For the numeric half, do not test through the app at all — drive the exact shader over known input colours in a raw WebGL2 context and read pixels back (six colours, maxErr 0/255), with `gl.getError()` after the upload as the direct evidence. Same family as the drawImage and console-buffer entries: when the readback cannot distinguish pass from fail, change the fixture, not the reasoning (trigger: two fixtures in a row produced screenshots that looked identical whether or not the fix was present).
- 2026-08-04 [skill]: Preconditions verified BY EYE are not verified. Three separate soak runs were invalidated by the same class of error — `layer.bg` pointing at Movie B, `layer.ds` pointing at Camera (dead over http on iOS, so displacement was invisible at any amount), `displace.amount` and `keyer` both still 0 while the chain was believed to include them, `mix.xfade` at 0.427 when the phase required 0 — and every one was confirmed "set correctly" by a human looking at sliders before the run. - 2026-08-02 [audit]: Promoting a prose lesson to an audit finds the cases the lesson never covered — write the test against the RULE, not against the incident. - 2026-08-05 [audit]: **A UI table keyed by id is a second registry, and a new entry is invisible until it is in BOTH.** Adding nine effects to `DEFAULT_FX_ORDER` wired them into the render chain completely — they ran, they were automatable, they saved and recalled — and left them absent from the signal-flow display, which is also the drag-to-reorder UI. Promoted immediately into the same audit and confirmed to fail with an entry removed. - 2026-08-05 [audit]: **A list persisted for ORDER is also a filter, and a filter silently deletes what it does not recognise.** `pipeline.setFxOrder` filtered a saved order to known ids, which is correct for stale ids and catastrophic for NEW ones: the chain order is captured by Display States and written into every `.imweb` file, so the moment an effect ships, every state on disk recalls with that effect missing from the chain. Row present, slider moves, readout updates, nothing renders — and the natural conclusion is that the new effect is broken, not that a five-year-old state is filtering it out. Unknown-but-current ids must be APPENDED at their default position rather than dropped. Same family as the capture-base entry (2026-07-30): appending to a list is safe, but anything that persists a SUBSET of that list needs a merge on load, not a filter (trigger: found while adding effects, before shipping — every effect in this release would have failed to appear for any saved state).
- 2026-08-05 [skill]: **`vite preview` builds its file map at STARTUP, so a rebuild is not served until the server is restarted** — and the symptom is indistinguishable from the service-worker cache trap above it. Three unregister/clear/force-reload cycles all kept loading the old bundle hash while `fetch('/index.html', {cache:'no-store'})` returned the NEW one; the SW was innocent. Settle which layer is stale by comparing `document.scripts[0].src` against a no-store fetch of index.html: if they disagree the PAGE is stale (SW/browser cache), if they agree and both are old the SERVER is stale (restart it). Restart preview after every build as a matter of course. Related: ImWeb registers `beforeunload` via `addEventListener`, so `window.onbeforeunload = null` cannot remove it and scripted navigation in the owner's tab is cancelled by the Leave-site dialog — verify in the Browser pane instead, which takes `force: true`, has its own localStorage (the owner's live patch is never touched) and starts from defaults; note its camera is blocked, so use FG = SDF over a Noise BG as the fixture (trigger: ~10 tool calls spent proving a service worker was not the problem).
- 2026-08-05 [audit]: **A hazard that only exists ACROSS passes cannot be caught by a guard that compares values within one.** The feedback transforms ping-ponged through the same two render targets that held the composited live frame, so whether the second transform overwrote it depended on how many passes the keyer/chroma/warp chain had run earlier that frame — parity, not intent. When it landed wrong the blend received the transformed prev frame as BOTH inputs and the live picture vanished, which reads as an artistic property of feedback rather than as a buffer bug, and comes and goes as unrelated effects are toggled. `_pass()`'s identity guard is structurally unable to see it: nothing is aliased at the moment of the write; the clobbered texture is read LATER. CLAUDE.md's "identity checks beat flags" is the right rule for aliasing and says nothing about lifetime — the fix for lifetime is a dedicated target (as the mix buses already do), and the invariant belongs in a static audit because a still frame cannot show it.
